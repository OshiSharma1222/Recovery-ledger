The problem

A quarter of the money cannot be recovered by anyone, ever.

In India, UPI Autopay and e‑mandates fail in ways cards do not. Mandates expire, amount caps get breached, customers revoke permission silently. All the merchant receives is one short string from the bank, and almost every system answers it the same way: retry on day one, three and five.

Low balance is a delay

The customer is between paychecks. Retry just after payday and the money is usually there. Retry two days before and it is a coin flip.

An expired mandate is a wall

The permission to charge is gone. The bank refuses every attempt, forever. No retry schedule, however clever, recovers a single rupee.

26% of this ledger is unrecoverable by construction. A fixed schedule spends three attempts on each of those rows every cycle and recovers nothing, which is the case for treating recovery as resource allocation.

How it works

Four steps, and one of them is stopping.

Detect

payment_cancelled

A debit bounces or a chargeback lands. Either becomes one row with the raw bank code exactly as received.

Diagnose

MANDATE_REVOKED

That code is ambiguous alone. Joined with the merchant's own mandate record it resolves, at 96.3% accuracy.

Decide

retry_at

Each cause has one action that can work: retry at a learned moment, renew the mandate, split a capped debit.

Stop

ABANDON

When nothing can work the engine spends nothing, and the saved attempts go where money can come back.

Chargebacks flow through the same ledger and the same statuses with a different action set, including a "do not contest" verdict when a case cannot be won. Adding them required no schema change at all. Customer contact is capped at two messages per case, because recovery is not allowed to become spam.

Beating a naive schedule proves little, since commercial products already optimise when to retry. So I built that competitor from my own parts: the identical learned timing model, best moment every time, but blind to the cause. Understanding the cause still beats it by +23.1% on 39% fewer attempts. That gap is the contribution, isolated as one number.

Honesty, and what is next

The limitation, stated first.

The customers are simulated and I authored that world, so this measures policy quality against a stated model, not production reality.

What protects the result: the simulator's parameters were frozen and committed before a single line of the policy engine existed, verifiable in one command of git history; the ranking holds across twenty unseen seeds; and the harness warns if any policy beats the oracle, which caught a real bug in my own favour before it reached the README. What is real: the Razorpay error codes, the RBI e‑mandate constraints, and the Visa and Mastercard dispute codes.

  • Verify the RBI figures against the primary circular, not secondary reporting.
  • Learn the ambiguous code mappings from data instead of ruling them.
  • Respect per‑rail re‑presentment caps as a policy constraint.
  • Add a third money source, such as refund abuse, to prove the ledger extends again.
